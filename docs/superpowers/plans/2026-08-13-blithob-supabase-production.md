# Blithob Supabase Production Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Connect the existing unified Blithob Professionals frontend to the Blithob Supabase project with durable authentication, Postgres persistence, RLS-protected workflows, private evidence storage, and release verification.

**Architecture:** Keep the existing React routes and pure domain selectors, replace browser domain persistence with a Supabase-backed repository, and keep workflow mutations transaction-safe in Postgres RPCs. Use a compatibility local adapter only when Supabase environment variables are absent so the existing unit suite remains deterministic; production builds with configured Supabase use Auth and remote data exclusively.

**Tech Stack:** React 19, TypeScript, Zustand, Supabase JS, Supabase CLI migrations, PostgreSQL functions/RLS, Vitest, Testing Library, Playwright, Netlify.

- [ ] **Step 1: Create the migration test contract.**

The SQL test must assert that the migration creates the expected enums,

- [ ] **Step 2: Write the migration.**

Create the enums and tables from the approved design in dependency order:
`profiles`, `professionals`, `services`, `service_requirements`,
`service_enrolments`, `service_requirement_progress`, `readiness_reviews`,
`jobs`, `job_references`, `assignments`, `submissions`,
`assignment_reviews`, `payments`, `notifications`, and `activity_events`.
Add `updated_at` triggers, Auth profile/email synchronization, the partial
active-enrolment index, `(job_id, professional_id)` uniqueness,
`(assignment_id, version)` uniqueness, and one payment per assignment.

- [ ] **Step 3: Add authorization helpers and RLS policies.**

Add locked `security definer` helpers for `is_admin()`, `is_professional()`,
`current_professional_id()`, and Lead checks. Enable RLS on every application
table. Allow Admin reads/writes where appropriate, own Professional reads and
profile updates, routed Lead reads, and deny direct writes that would bypass a
workflow transition.

- [ ] **Step 4: Add transactional workflow RPCs.**

Implement `set_requirement_progress`, `submit_service_enrolment`,
`review_service_enrolment`, `add_job_assignments`, `start_assignment`,
`submit_assignment`, `review_assignment`, `complete_assignment`,
`cancel_assignment`, `record_payment`, `correct_paid_payment`, and
`mark_notification_read`. Each function validates the caller and current
status, applies the state change, inserts activity/notifications, and returns
the changed row or a stable result. `complete_assignment` creates exactly one
payment in the same transaction.

- [ ] **Step 5: Add private Storage buckets and policies.**

Create `readiness-evidence`, `assignment-submissions`, and `payment-receipts`
as private buckets. Add object policies keyed by authenticated profile and
related database record. Keep file names as metadata and use generated object
paths.

- [ ] **Step 6: Apply and verify the migration.**

Run:

```powershell
supabase db push --linked
supabase db lint
```

Then run the SQL assertions against the linked database using the Supabase SQL
editor/CLI-supported test path. If the CLI cannot run SQL tests remotely,
execute the same assertions against a local database when Docker is available
and retain the SQL test file for CI.

- [ ] **Step 7: Commit the schema checkpoint.**

